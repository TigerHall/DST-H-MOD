# 2026-11-15

## hslot v3.5.1：蓝色月眼空间 160 格 + 列表式界面（首版）

### 方案决策（重要）
- 用户原先有 6 个口袋空间，最终决定**只把蓝色月眼（hslot_container）做大**，其余 5 个不动
- 容量定 160 格（真实 container），列表式 UI，不做显示聚合，不做真堆叠
- 不做真堆叠的原因：鸟有 health、鱼有 perishable，加 stackable 会状态共享（一条烂整堆烂）

### 参考资料结论
- **简易存储 3383078008**（~6800 行）：fakecontainer + fakeitem 纯数据方案，为跨世界远程访问设计，所以能上千件；代价是失去原版交互
- **空间戒指 3228163175**（modmain 加密）：多页真实容器 + 分页，modinfo 明确写「官方容器机制，格子/物品多了会卡，建议总格数不超过 700」
- **储藏室（新地窖）2784048339**（~1300 行）：真实 container + 自定义 slotpos 网格 + 升级贴图，扩容的正确姿势
- **额外的格子 2823530744**（~1280 行）：改 GLOBAL.MAXITEMSLOTS + 背包格数
- 官方源码里就有 `widgets/truescrolllist.lua`（TrueScrollList），不用从简易存储偷

### 实现
- `scripts/prefabs/hslot_container.lua`：`params.hslot_container.widget.numslots = 160`，slotpos 只留 16 个占位
  - `containers.widgetsetup` 优先用 `widget.numslots`（containers.lua:15），`SetNumSlots` 只允许变大（container.lua:116），所以老档直接扩容安全
- `scripts/widgets/hslot_vault_list.lua`（新，185 行）：面板 + TrueScrollList + 每行一个官方 `InvSlot` + 名称 Text
  - **关键取巧**：列表行内嵌官方 `InvSlot(num, "images/hud.xml", "inv_slot.tex", owner, container.replica.container)`，点击/右键/放入的交互全部走原版 `InvSlot:Click`，不用自己写 RPC；数量/耐久由 `ItemTile` 自己画
  - 虚拟滚动：滚动时只改 `row.slot.num` + `SetTile`，不重建 widget
  - 末尾补一个"空槽位"行（指向第一个空槽），拖物品上去即存入
  - 容器变化监听 `itemget` / `itemlose` / `refresh`，0.12 秒合并刷新
- `modmain.lua`：客户端 hook `widgets/containerwidget`
  - `Open`：prefab == "hslot_container" 时 `self:Hide()` + 创建列表挂到 `ThePlayer.HUD`
  - `Refresh`：hslot 时**直接 return**（官方网格只有 16 个 inv，items key 到 100 会越界崩溃）
  - `Close`：Kill 列表 + `self:Show()`

### 已知风险
- `containers.MAXITEMSLOTS` 会被抬到 160，而 `prefabs/container_classified.lua:1057` 是**按 MAXITEMSLOTS 给每个容器实体预建 net_entity**，等于所有箱子/冰箱都多建 160 个 netvar → 可能是卡顿来源（空间戒指说 700 格就卡，大概就是这个）
- TrueScrollList 第 8 个参数 `scrollbar_offset` 传的是**数字**（相对 scissor 右边偏移），不是 table（truescrolllist.lua:79 会自己拼成 {x,y}）
- ItemSlot 没有 Refresh/SetNum 方法，改 num 后必须手动 `SetTile(container:GetItemInSlot(num))`

## hslot v3.5.2：列表加左侧分类筛选

- 分类按钮：全部 / 工具 / 武器 / 装备 / 食物 / 魔法 / 材料，用 `TEMPLATES.StandardButton(onclick, txt, {w,h})`
- 分类规则**不写死 prefab**：遍历 `CRAFTING_FILTERS[<FILTER>].recipes` → `AllRecipes[recipe].product` 反查，建立 `CATEGORY_OF[prefab][filter] = true`
  - 可用分类名（recipes_filter.lua）：TOOLS / LIGHT / REFINE / WEAPONS / ARMOUR / CLOTHING / RESTORATION / MAGIC / DECOR / STRUCTURES / CONTAINERS / COOKING / GARDENING / FISHING
  - 简易存储的 terminalfn.lua 也是同一套做法（另有手工分类表补充 REFINE/MAGIC 漏网的）
- 布局：SIDEBAR_W = 118，面板加宽，列表整体右移 SIDEBAR_W/2
- 选中按钮文字染成金色 `(1, 0.86, 0.45)`，其余灰色
- 不做搜索框（用户明确不要）
- 容量文案：全部时「已用 x / 160 格」，筛选时追加「筛选 n 项」

### 关于「多建几个小口袋空间凑成大的」可行性结论
- **技术障碍**：客户端只能拿到「自己 open 的容器」的物品（container_replica:GetItems 依赖 `self.opener`），要显示 N 个容器就必须 Open N 次 → HUD 会为每个创建 ContainerWidget（可全部 Hide），复杂度上升
- **收益边界**：`containers.MAXITEMSLOTS` 抬高影响的是 `container_classified.lua:1057` 给**每个容器实体**预建的 net_entity 池
  - 单容器 160 格：世界里 50 个箱子 → 50 × 160 = 8000 个 net_entity
  - 10 个 16 格小容器：50 × 16 + 160 = 960 个
  - 差异确实存在，但每个 net_entity 很小，实际卡不卡要实测
- **结论**：先测 160 格实际体感；卡了优先把容量降到 80~100（一行改动），而不是重构多容器

## hslot v3.5.3：修复读档崩溃 `wrong number of arguments to 'insert'`（槽位池耗尽）

- 现象：读档 `SpawnSaveRecord` → `hslot_container` 的 `WidgetSetup` → `container_classified.lua:15` 崩，
  堆栈 `numslots=160, curslots=0, i=21`
- 根因：官方 `containers.lua:2498-2500` 在**文件加载末尾**一次性算出 `MAXITEMSLOTS`（官方最大 20）；
  mod 的 `params.hslot_container` 是 `require("containers")` **之后**才注册的，没被统计进去
  → `container_classified.lua:1057` 只预建了 20 个 `net_entity` 池 `_itemspool`
  → `InitializeSlots(160)` 第 21 次 `table.remove(池, 1)` 空表返回 **0 个值**（Lua 5.1 `tremove` 在 e==0 时 `return 0`）
  → 外层 `table.insert(inst._items, <无值>)` 只有 1 个参数 → 报参数个数错误
  （报错文本很误导，本质是"槽位池耗尽"，与列表 UI 无关）
- 修复：`scripts/prefabs/hslot_container.lua` 顶层加
  `containers.MAXITEMSLOTS = math.max(containers.MAXITEMSLOTS, HSLOT_VAULT_SLOTS)`，
  并把 `numslots` 改用同一个常量 `HSLOT_VAULT_SLOTS = 160`（单点定义，防两处不同步）
- 约束（重要）：必须在任何 `container_classified` 被 SpawnPrefab 之前（mod 加载阶段）设置，
  且**服务端/客户端都要生效**（prefab 文件顶层两端共享），否则 netvar 编号错位、物品同步全乱；
  不能用 `AddPrefabPostInit` 事后补池子 —— net_entity 必须在 `entity:SetPristine()` 之前创建
- 社区做法一致：可升级箱子 2484725102 / 储藏室 2784048339 / 棱镜 1392778117 /
  生活质量更新 3454347475 都是手动抬高 `containers.MAXITEMSLOTS`
- 代价（见 v3.5.1 已知风险）：抬到 160 会让**所有**容器 classified 预建 160 个 net_entity；
  实测卡就只改 `HSLOT_VAULT_SLOTS` 降到 80~100
- `modinfo.lua` version 3.5.2 → 3.5.3

### 生效条件（必须重启进程，但不删档）
- mod 脚本由 `require` 加载一次并进 `package.loaded` 缓存，改磁盘文件不会热重载；
  `container_classified` 的 netvar 池又在世界加载 spawn 时、于 `SetPristine()` 前固化
  → **必须完全退出游戏客户端再启动**（只退出世界重进不一定生效）
- 专用服务器：重启服务端 + **所有客户端同步到 3.5.3**，`MAXITEMSLOTS` 两端必须一致，
  否则 netvar 编号错位、物品同步全乱
- 不需要删档/新建世界：崩溃在 `PopulateWorld` 读档阶段，存档未被改写；
  `SetNumSlots` 只增不减，旧档 ≤20 格物品照常恢复

### 踩坑入库
- 新坑「容器扩容 >20 格必须抬高 `containers.MAXITEMSLOTS`」写入技能 3 份副本：

## 评估：紫/橙/黄三个空间同样改造，性能影响

每个 container_classified 恒定 160 个 netvar，与 numslots 无关。

  而 `containers` 在 modmain 里没有全局声明（是 require 的局部）→ 直接 error。
  因为诊断块在 `TogglePocketDimensionChest` 里，打开空间时就把 RPC 打断 → 崩溃。
- 修法：改成 `local _containers = require("containers")` 再取 `.MAXITEMSLOTS`
- **教训（补充到既有 strict 坑）**：strict 模式下不仅 `foo` 会报，
  **`GLOBAL.foo` 同样会报**，因为 GLOBAL 是 _G 的引用。要读引擎全局用 `GLOBAL.rawget`，
  或者干脆 require 一个局部引用。
- `modinfo.lua` 3.6.4 → 3.6.5

### 简易存储（3383078008）的做法
`main/hook.lua:426-460` —— **`fake_opencontainers`**：
```lua
AddComponentPostInit("inventory", function(self)
    self.fake_opencontainers = {}
    local function hook_opencontainers(fn_name)
        local old_fn = self[fn_name]
        self[fn_name] = function(self, ...)
            local old = shallowcopy(self.opencontainers)
            for k in pairs(self.fake_opencontainers) do self.opencontainers[k] = true end
            local ret = { old_fn(self, ...) }
            self.opencontainers = old
            return unpack(ret)
        end
    end
    -- 延迟一帧挂，避免被覆盖
    local hooklist = { "FindCraftingItems", "GetCraftingIngredient", "GetItemByName", "RemoveItem", "Has" }
end)
```
打开终端时 `inventory.fake_opencontainers[inst] = true`，关闭时清掉。
即：**把「虚拟容器」临时塞进 opencontainers 再调用原函数，用完还原**。
这是为「容器实体不存在/不受官方管理」的情况准备的；我们是真实实体，理论上不需要。
