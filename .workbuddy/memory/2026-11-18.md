## 格子优化 hslot v3.8.1：蓝眼 160 空间三个问题

### 问题1：分辨率缩放（1080p 偏大 / 4K 偏小）
- 根因：面板挂在 `controls.containerroot`（SCALEMODE_PROPORTIONAL + MAX_HUD_SCALE=1.25，
  constants.lua:43）。4K 下 PROPORTIONAL 理论放大 1.8 被钳到 1.25 → 相对屏幕显小。
- 修法：`hslot_vault_list.lua` 新增 `ScreenScaleCompensation()`，按屏幕高度线性补偿
  1080p≈0.95 / 1440p≈1.0 / 4K≈1.10（±10% 有界），`self:SetScale(PANEL_SCALE * 系数)`。
- 没有重犯坑 #58 的「按目标占屏比例硬算双重换算」。

### 问题2：两玩家蓝眼仓库滚动同步（A 放东西 B 也跳）
- 根因：四色仓库是**世界单例容器**（`SetPocketDimensionContainer`，全服一个 hslot_container）。
  A 放入 → 服务端 push itemget（container.lua:538）→ container_classified 广播给所有
  opener（container_classified.lua:362）→ 每个客户端的 `onitemget` 都设 `_pending_slot`
  → 都 ScrollToDataIndex。
- 修法：`onitemget` 只在「本地玩家背包刚 itemlose」的 0.5s 时间窗内才认领 `_pending_slot`；
  监听 `ThePlayer:ListenForEvent("itemlose", ...)`，OnDestroy 里 RemoveEventCallback。
  别人上传只 QueueRefresh 不滚。

### 问题3：旧存档不能制作取料（待验证）
- 现象：新存档 OK；旧存档能上传物品，但制作时材料不识别。
- 链路：`inventory_classified:Has`（user_classified）→ `inventory_replica:GetOpenContainers()`
  → 对每个容器 `container_replica:Has()` → 需 `self.classified ~= nil and self.opener ~= nil`。
- mod 补丁（modmain.lua:1462-1481）靠 `k:HasTag("pocketdimension_container")` 把容器塞进
  `HUD.controls.containers` 列表，让 GetOpenContainers 收进去。
- 高概率根因：旧存档里口袋容器实体是**读档时由 AddPrefabPostInit(itemget) 恢复**的，
  `inst.Network:SetClassifiedTarget(inst)`（hslot_container.lua:160）在存档实体上的 opener /
  classified 绑定时序可能与新 spawn 不同；或 `onanyopenfn` 里多人/单人切换 target 的时机问题。
- 已在 modmain.lua:1712-1775 埋了 vault_debug 诊断打印（in_opencontainers / opener / cls / Has），
  需用户开诊断复现贴日志再定。

### v3.8.2：缩放补偿加大（用户反馈 ±10% 不够）
- 截图实测：1080p 面板占屏高 ~86%，4K ~42%（差整整一倍）。
- 根因确认：父级 PROPORTIONAL 放大被 MAX_HUD_SCALE=1.25 钳死，屏幕 1080→2160
  面板实际只放大 ~1.25 而非 2，所以 4K 显小、1080p 显大。
- 修法：`ScreenScaleCompensation()` 改成**无上限线性补偿**：
  `0.85 + t*0.6`，t=(screenh-1080)/1080，clamp[-0.3,1.3]。
  → 1080p≈0.85 / 1440p≈1.05 / 4K≈1.45。1080 缩小向制作栏靠，4K 放大补回钳掉的比例。
- 制作栏挂 left_root 同样受 1.25 钳制，但其设计尺寸更小所以看着协调，面板须自己补。
- ⚠️ 若补偿后过冲/不足，只调 `0.85` 基准和 `0.6` 斜率两个数。

### 为什么不能直接照搬简易存储的 0.6（源码比对结论）
- 用户质疑「源码都有，写法一样，只是格子排版不同，为何尺寸不同」。逐层比对：
- **格子设计尺寸确实一样**：两边格子中心间距都是 80
  （简易存储 row_w 64 + row_spacing 16 = widget_width 80；hslot CELL=80），
  图标都是官方 `inv_slot.tex` 64px，两边 scrolllist 内部都没有对格子做缩放。
- **缩放链也基本一样**：两边 root 都挂 `containerroot.parent`，都 `SetScale(GetHUDScale())`
  + hook SetHUDSize。外层 containerroot 的 PROPORTIONAL(钳1.25) 对两者同等作用。
- **真正的差异（关键）**：0.6 所在的层级不同 ——
  - 简易存储：`terminalwidget.lua:813-815` `gridroot:SetScale(0.6)`，
    gridroot 是**只包住网格**的层（gridroot → grid → 格子）。面板边框/筛选/按钮
    在 `self.root` 等其他兄弟层，**不受 0.6 影响**。
  - hslot：原 `self:SetScale(PANEL_SCALE)` 作用在**整个面板**（边框/筛选/网格/按钮全在内）。
    同样 0.6 时，hslot 网格格子 = 80×0.6×GetHUDScale，简易存储网格格子 =
    80×0.6×GetHUDScale —— 理论上网格该一样大。
- 但同图像素实测（1920 原图扫一行亮度上升沿）：简易存储格子周期 **50px**，
  hslot(PANEL_SCALE=0.6) **40px**，差 1.25 倍 = MAX_HUD_SCALE。
- 1.25 来源 = **外层 containerroot 的 SCALEMODE_PROPORTIONAL + SetMaxPropUpscale(1.25)**。
  两者虽挂同一父层，但**挂载时机不同**：简易存储 AddClassPostConstruct 在 controls 构造期
  就建 terminalrroot；hslot 的 list 是**打开容器时**才动态 AddChild 到 hslot_vault_root，
  且 hslot_vault_root 的 SetScale(GetHUDScale) 只在构造+SetHUDSize 时设。
- 结论：与其纠结 1.25 的确切来源，**实用做法就是同图像素实测定标**（PANEL_SCALE=0.75）。
  要真正「一样写法」需把 hslot 改成 gridroot 独占缩放层（工程量大，本次不做）。
- 关键事实：0.6 在这两个 mod 里含义不同（一个只缩网格、一个缩整面板），不是同一个 0.6。

### 官方无限空间可行性调研（bundlewrap / pirate_stash）
- **pirate_stash**（prefabs/pirate_stash.lua）：就是带 `inventory` 组件的实体，
  `maxslots = TUNING.PIRATE_STASH_INV_SIZE`，`OnSave/OnLoad` 存 nextslot；
  带 `preserver` 组件（perish/temperature 速率 0 = 不变质）。挖出时把物品甩一地。
  → 本质：一个**世界里的固定容器实体**，槽位数由 tuning 定，可改大。
- **bundlewrap/unwrappable**（components/unwrappable.lua）：打包时 `WrapItems` 把每个物品
  `item:GetSaveRecord()` 序列化进 `self.itemdata` 表（纯数据，不是实体！），OnSave 存 data.items；
  拆包 Unwrap 时 `SpawnPrefab(v.prefab, ...)` 重建。`peekcontainer=bundle_container` 只是 2x2 预览。
  → 本质：**把物品序列化成数据表存在 bundle 实体的 component 里**，零实体开销直到拆包。
- 结论方向：unwrappable 的「序列化存储」思路适合做无限空间（存 data record 表，不 spawn 实体），
  比当前遍历所有容器实体的方案更优；但需自建 UI + RPC + 存取逻辑。详见对话分析。
